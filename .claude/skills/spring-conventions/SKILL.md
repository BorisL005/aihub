# Spring backend conventions — AI Hub

Read `ARCHITECTURE.md` in the repository root before your first change in a session. It contains the decisions and their rationale; do not re-litigate them in code.

## Non-negotiable security rule (read this first)

There is no database-level row security (no RLS). Tenant isolation exists ONLY in application code. Therefore:

- Every query that touches `projects`, `entries`, `summaries`, `notes`, or `routines` MUST filter by the authenticated `user_id`, either directly or through an ownership join on `projects.user_id`.
- `user_id` comes exclusively from the validated JWT (`AuthenticatedUser` resolved from the security context). Never accept it from a request body, path, or query parameter.
- Every repository method that returns tenant data must have a test proving that user A cannot read or modify user B's rows. A repository method without such a test is an incomplete deliverable — the task is not done.
- If you find an existing query that violates this rule, fixing it takes priority over the task you were given. Flag it explicitly in your summary.

This rule exists because a single forgotten `WHERE user_id = ?` silently leaks another person's financial and health data. Nothing else in this document outranks it.

## Language and framework baseline

- Java 21 language level. Prefer records, sealed interfaces, pattern matching, and switch expressions over their legacy equivalents.
- Spring Boot 4.1 / Spring Framework 7. Blocking style on virtual threads — do NOT introduce WebFlux, Reactor, or CompletableFuture chains for request handling. A blocking call on a virtual thread is the intended pattern here.
- No Lombok. Records and modern Java remove most of the need; generated bytecode magic makes agent-written code harder for the owner to review.
- Constructor injection only in production code. No `@Autowired` on fields or setters. Single-constructor classes need no annotation. Exemption: test classes may use field injection for Spring-managed test fixtures - that is the idiomatic Spring test style.

## Code style (Oracle Java conventions, updated)

Follow the standard Oracle/Java conventions; the points below are the ones agents most often get wrong:

- 4-space indentation, no tabs. Line length soft limit 120.
- K&R braces (opening brace on the same line). Braces are mandatory even for single-statement `if`/`for`.
- Naming: `UpperCamelCase` types, `lowerCamelCase` members and methods, `UPPER_SNAKE_CASE` constants, lowercase dot-separated packages. No underscores or `$` anywhere else. No Hungarian notation, no `I`-prefixed interfaces, no `Impl` suffix unless there is genuinely one interface with one implementation forced by a framework.
- One top-level class per file. File name matches the class.
- Import order: `java.*`, `jakarta.*`, third-party, project. No wildcard imports.
- Javadoc on public API of each module (service interfaces, DTOs used in OpenAPI). Implementation details get regular comments only where the "why" is not obvious from the code. Do not write comments that restate the code.
- Declare variables at first use, one declaration per line. Prefer `final` for fields; use `var` only when the right-hand side makes the type obvious.

## Module structure

Single Maven project (multi-module later only if pain demands), package-per-feature under `dev.aihub`:

```
dev.aihub
├── ingestion/     # media intake, extraction pipeline, validation, entry persistence
├── query/         # question router, recipes, tool-loop, SSE streaming
├── routines/      # Quartz jobs, reminders, push notifications
├── projecttype/   # project_type catalog: schemas, prompts, metric templates
├── llm/           # Spring AI ChatModel wiring, model registry, llm_calls logging
├── security/      # JWT resource-server config, AuthenticatedUser resolution
└── common/        # shared value types, error handling, jOOQ infra
```

- Features depend on `llm`, `security`, and `common` — never on each other. If two features need the same code, it moves to `common` (value types) or gets its own package (behavior).
- Within a feature package: `XController`, `XService`, `XRepository`, plus records for requests/responses. No `dto`/`impl`/`util` sub-packages — keep the package flat until it exceeds ~15 files.

## API layer

- Controllers are thin: bind, validate, delegate, map to response record. No business logic, no direct jOOQ access.
- Request/response types are records annotated with Bean Validation (`@NotNull`, `@Size`, ...). Validation failures must surface as 400 with a structured error body — do not catch and swallow.
- The OpenAPI spec in `/api` is the contract with the Expo client. Any endpoint change must update the spec in the same PR; the TS client is generated from it. An endpoint that isn't in the spec doesn't exist.
- Trainer/chat answers stream over SSE (`SseEmitter`); everything else is plain JSON.

## Data access (jOOQ + Postgres)

- All persistence goes through jOOQ `DSLContext` in `*Repository` classes. No JPA, no Hibernate, no JdbcTemplate, no string-concatenated SQL.
- Always bind parameters through jOOQ's API. Never inline user input into SQL — this includes JSONB path expressions built from project_type metric templates: template SQL comes from the database (trusted, whitelisted), user input is only ever bound as parameters into it.
- `entries.payload` is `jsonb`. Access fields with `DSL.jsonbGetAttributeAsText(...)` / typed casts; add expression indexes in migrations when a recipe filters or aggregates on a hot field.
- Aggregations belong in SQL, not Java. If you are streaming rows out of Postgres to sum them in a loop, stop and write the aggregate query — this is an architectural rule (see ARCHITECTURE.md, trainer context layers), not a style preference.
- Transactions via `@Transactional` at the service layer. Repositories do not manage transactions.

## Migrations (Flyway)

- Files: `V{n}__{snake_case_description}.sql`, sequential integers, no gaps, never edit an applied migration — fix forward with a new one.
- Every table gets: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null default now()`. Tenant tables get `user_id` (or a FK path to it) with an index.
- JSONB columns that recipes query get a GIN index in the same migration that introduces the query pattern.
- Quartz tables come from the official Quartz DDL in their own migration; do not hand-modify them.

## LLM integration (Spring AI 2.0)

- All model access goes through the `llm` package's model registry, which resolves a `ChatModel` by the logical name stored in `project_type` (`extraction_model`, `answer_model`). Feature code never names a concrete provider or model id — providers are configuration.
- Structured extraction: `entity(...)` mapping onto a Java record + Bean Validation on that record. A response that fails validation goes to the manual-confirmation queue with the raw response preserved; never silently discard or "fix up" model output in code.
- Wrap outbound model calls with Framework 7 `@Retryable` (jittered backoff) and `@ConcurrencyLimit`. Do not add Resilience4j.
- Every model call — success or failure — is logged to `llm_calls` (prompt version, model, token counts, latency, validation outcome). A code path that calls a model without logging is a bug.
- Prompts live in versioned resources (`resources/prompts/{name}/v{n}.st`), not in string literals. The prompt version goes into the `llm_calls` row.
- Spring AI 2.0 is a fresh GA: when its API surprises you, check the official docs and release notes rather than pattern-matching from pre-2.0 blog posts — much of the community material targets 1.x and no longer compiles.

## Testing

- Integration tests use Testcontainers with real Postgres 17 + pgvector. Do not mock the database; do not use H2 — JSONB and pgvector behavior is the point.
- Mock only true externals: LLM providers (stub `ChatModel`), transcription, R2, Expo Push.
- Required per feature: (1) the tenant-isolation test from the security rule, (2) validation-failure paths (invalid extraction → confirmation queue), (3) recipe SQL correctness against seeded fixture data.
- Extraction quality is NOT tested with unit tests — it is measured by the eval harness (see the `llm-extraction` skill). Do not write brittle assertions on model output text.
- Test names describe behavior: `rejectsEntryFromDifferentUser`, not `test1`.

## Things that end a review immediately

- A tenant-data query without user_id filtering, or user_id taken from request input.
- Field injection, Lombok, WebFlux/reactive types, JPA entities.
- SQL built by string concatenation or formatted strings.
- A model call without an `llm_calls` log row, or a prompt inlined as a string literal.
- Editing an already-applied Flyway migration.
- An endpoint changed without the OpenAPI spec updated in the same change.
- Business logic in a controller, or aggregation loops in Java over data Postgres could aggregate.
